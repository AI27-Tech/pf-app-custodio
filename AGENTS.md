## AGP 9 gotchas (most online examples use the removed old DSL)

- `compileSdk` must use the new block form: `compileSdk { version = release(37) }`. A bare `compileSdk = 37` will not compile.
- Minify/R8 lives in `buildTypes.release.optimization { enable = ... }`. `minifyEnabled` / `isMinifyEnabled` no longer exist. Release currently has R8 disabled (`optimization { enable = false }`).
- Keep rules live in `app/src/main/keepRules/` (existing `rules.keep`), not `proguard-rules.pro`.
- El plugin de Crashlytics (`com.google.firebase.crashlytics`) está versionado en el catálogo y **aplicado en `:app`** desde B7, con el SDK inicializado en `EchoApplication` y recolección explícita en el manifest. `mappingFileUploadEnabled`/el bloque `firebaseCrashlytics { }` NO se usan: el accessor no genera con AGP 9 y con R8 apagado no hay mapping; el reporte real queda activo cuando exista la consola (carril A).
- La firma de release lee `keystore.properties` (gitignored) con `storeFile`/`storePassword`/`keyAlias`/`keyPassword`; si el archivo no existe, `release` queda sin firmar. El keystore vive en `app/keystore/release.jks` (gitignored por `*.jks`) y hay que resguardarlo fuera del repo: es lo único que permite actualizar instalaciones ya desplegadas sin desinstalar (y desinstalar borra la cola local de evidencia). **Regla de la casa: en cuanto el primer APK llegue a un equipo real, ese jks queda congelado para siempre** — cambiarlo después obliga a reinstalar desde cero.

## Config notes

- `org.gradle.configuration-cache=true` in `gradle.properties` — keep build-script edits configuration-cache compatible.
- `local.properties` (machine-local `sdk.dir`) is gitignored; never commit it or hard-code SDK paths.
- App name is "Echo" (`rootProject.name`, manifest label via `@string/app_name`, theme `Theme.Echo`, `EchoApplication`, `EchoTheme`, `EchoDatabase`).
- **Orientación: `MainActivity` NO declara `android:screenOrientation` (decisión del 2026-09-28, no lo repongas sin que lo pida el humano).** La cronología del atributo fue `portrait` (commit base) → `fullSensor` (por el autor del proyecto, después de la auditoría) → **sin atributo**. El valor ausente deja la orientación en `unspecified`, que es la primera de las dos vías que ofrece la guía vigente de Android (*Restrict app orientation on phones*: *"either avoid declaring the `screenOrientation` element of the app manifest … or set screen orientation to `fullUser`"*), y hace que la app **respete el ajuste de rotación automática del usuario** — con `fullSensor` el custodio veía la app girar aunque tuviera la rotación apagada. Con `targetSdk = 37` **no hay a qué volver**: desde Android 17 las restricciones de orientación se ignoran **siempre** en sw ≥ 600 dp y el opt-out ya no existe, así que `portrait` no arreglaría tablet y solo volvería a romper el teléfono. Lo que queda pendiente es de implementación, no de orientación: los destinos sin `verticalScroll` (`Login`, `ReporteAbierto`, `Audio`, `Ajustes` — hallazgo A3.9 de `docs/AUDIT.md`), que se rompen en horizontal para quien tenga la rotación automática activada. Detalle en A9.
- **El renombrado de "App Custodio" a "Echo" (2026-09-25) fue deliberadamente parcial.** Cambiaron: la etiqueta del launcher (`app_name`, que es también el nombre que ve App Distribution), `rootProject.name`, `Theme.AppCustodio` → `Theme.Echo`, `AppCustodioApplication` → `EchoApplication`, `AppCustodioTheme` → `EchoTheme` y la clase `AppCustodioDatabase` → `EchoDatabase`. **NO cambiaron:**
  - **El package** (`com.ai27.app.custodio`) y el `applicationId`: la razón ya no es "no romper instalaciones desplegadas" (a 2026-09-25 **no había ningún equipo en campo, todas las instalaciones son frescas**), sino que `app/google-services.json` amarra la app Android de Firebase al `package_name` con su `mobilesdk_app_id`. En la variante clara **no queda ni un píxel casi blanco** (verificado: 0), que es lo que ensures que no haya un halo invisible sobre el lienzo claro.

## Nota: quirk del Emulator Suite (Firestore)

- Con la plantilla 13.29.0 del Firebase CLI, el emulador de Firestore evalúa las reglas de lectura de `list`/`runQuery` muestreando documentos que llegan **sin `custodioUid`**, y responde 403 `Property custodioUid is undefined on object. for 'list'` aunque el documento real tenga el campo. Verificado con el emulador corriendo como proyecto `custodio-906e7268`.
- No afecta a la app: el pipeline solo usa `get` por llave, `set`/`update` y el `get()` cruzado de las reglas de Storage; el historial lee de Room y nunca lista Firestore. Para validar contra el emulador, consulta por llave (REST `GET .../documents/reportes/{id}`) en lugar de `list`. `npm test` (rules-unit-testing) usa su propio motor in-process y no se ve afectado.
- Otro quirk (v1.19.8 del emulador Java de Firestore): un `get()` interno de una regla —p. ej. el de `esAnalista()` leyendo `config/analistas` o el de `duenoDelReporte()`/`reportePerteneceA()`— **revienta la regla entera con "Service call error" si el documento consultado no existe**, en lugar de devolver `null`. Por eso las ESCRITURAS de custodio no consultan `config/analistas` (un emulador recién iniciado sube sin depender de la lista) y el reporte se crea ANTES que el medio. Si un `get()` de una regla falla de forma rara: crea el documento que lee y reintenta.
- El analista del panel se autoriza por CORREO en `config/analistas.correos` (no por uid ni claims). En `emulators:start` la lista hay que crearla una vez (Emulator UI `http://127.0.0.1:4000/firestore` o REST con `Authorization: Bearer owner`; ver README "Alta de analistas").
